## 0. 链路全景

```
① 分组     GET  /iptve.php                      → HTML，5 个 <a href="?tid=xx">
② 频道     GET  /iptve.php?tid=<tid>&app=517    → HTML，<a href="?act=play&tid=..&id=..">名称</a>
③ 播放页   GET  /iptve.php?act=play&tid=&id=     → HTML，<option value="密文"> × 13 + 节目单
④ 解密     option → 反转 → b64解 → XOR → b64解 → 换token → 去盐 → eplay2.php URL
⑤ 真流     GET  eplay2.php?...  → 302 ─┬─→ t62.iptv200.com:8443/live/cctv1.flv?sign=..   （直连）
                                        └─→ /v/migu8.php?...  → 302 → 真流               （二级中转）
```

## 1. 站点与镜像

| 项    | 值                                                                                         |
| ---- | ----------------------------------------------------------------------------------------- |
| 默认接口 | `https://api1.2026016.xyz`                                                                |
| 同源镜像 | `https://api1.2026016.xyz` → `https://api.2026016.xyz` → `https://api2.2026016.xyz`（按序回退） |

## 2. 请求头（命门，缺一拿不到线路）

```http
User-Agent: Mozilla/5.0 (Linux; Android 9; SM-N9700 Build/PQ3B.190801.01311438; wv) AppleWebKit/537.36 (KHTML, like Gecko) Version/4.0 Chrome/91.0.4472.114 Mobile Safari/537.36 diashizhb LT-APP/48/517/YM-RT/
x-requested-with: com.sldv.okstuffx
Cookie: adReward=1; iptvad=1; appVer=517
Accept: */*
Accept-Language: zh-CN,zh;q=0.9
```

三个要素**互相呼应、缺一不可**：

1. UA 里的 `LT-APP/48/517` —— 接口校验点
2. `x-requested-with: com.sldv.okstuffx` —— 包名
3. Cookie 里的 `appVer=517` —— 与 UA 的 517 对应

**同一 URL，两套返回**（`/iptve.php?act=play&tid=ys&id=1` 实测）：

| 请求头                  | 返回                                      |
| -------------------- | --------------------------------------- |
| 完整头                  | 200，**18408 字节，13 个 `<option>`，含加密块** ✅ |
| 裸 UA `LT-APP/48/517` | 200，7667 字节，**0 个 option**，只剩节目单 ❌      |

★ 但 **`eplay2.php` 不需要任何头** —— 裸请求即 302。  
→ 「app 头」只决定**能不能拿到线路列表**，不决定**能不能播**。

## 6. ④ 加解密算法（核心）

### 6.1 密文到明文的六步（`core.rs::decrypt_page`）

伪代码：

```python
s0 = option_value            # 站点给的密文串
s1 = s0[::-1]                # ① 字符反转
s2 = b64decode(s1)           # ② base64 解码 → 字节串
s3 = bytes(a ^ key[i % len(key)] for i, a in enumerate(s2))   # ③ XOR
s4 = b64decode(s3)           # ④ 再 base64 解码 → 字节串
s5 = s4.replace(b"token="+old, b"token="+new)   # ⑤ 换 token（old→new）
s6 = s5.replace(key_seed, b"")                  # ⑥ 去掉密钥前缀（盐）
if not re.match(rb"^https?://", s6): skip        # 只认 http(s) 开头
```

最后补全：**若 URL 里没有 `type=`，追加 `&type=.flv`**。

★★ ②④ **必须按字节做**，绝不能先转文本。  
XOR 产物是任意字节，Python 侧用 latin1 逐码点保真；Rust 侧必须用「字节级 base64 解码」  
（`b64d_bytes`）。一旦用 `from_utf8_lossy`，非 UTF-8 字节会被替换成 U+FFFD，  
**长度和内容双错，整条线路静默解坏**。

### 6.2 XOR key 怎么来：已知明文攻击

key 不是页面里的明文常量（网页版 678 系才是明文），app 版必须**反推**。

**第 1 步：从页面挑两段 `<script>`**

| 块            | 判定特征                                                         | 用途     |
| ------------ | ------------------------------------------------------------ | ------ |
| **assign 块** | 含 `var x = "";` 形式、含 `split("").reverse()`、**不含** `function` | 变量赋值表  |
| **ent 块**    | 含 `function f(a,b){ … .reverse() … }`                        | 解密函数本体 |

**第 2 步：从 ent 块抓变量名**

```regex
# XOR 密钥变量（函数调用的第二个实参）
\(\s*\w+\s*,\s*(\w+)\s*\)
# token 新旧
"token="\+(\w+)\s*,\s*"token="\+(\w+)
```

**第 3 步：解析 assign 块里的变量值**（`parse_env` + `concat_val`）

assign 块的写法是 JS 常量拼接式，必须先求值：

```js
var qnvur = "abc" + "def".split("").reverse().join("") + "ghi";
```

- 先把 `"xxx".split("").reverse().join("")` 就地替换成**反序字符串**
- 再按顺序拼接所有 `"..."` 字面量
- `var a = b;` 形式的别名要跟随一次（指向另一个变量）

★ `key_seed`（盐）= 这样解析出来的密钥变量值；`old` / `new` = 两个 token 变量值。

**第 4 步：造候选明文，长度比对即命中**

```python
s0   = b64decode(option_value[::-1])          # 第 1 条线路（p=0）
for tmpl in [
    f"{api}/eplay2.php?token={old}&tid={tid}&id={cid}&p=0&type=.flv",   # 模板①
    f"{api}/eplay2.php?token={old}&tid={tid}&id={cid}&p=0",             # 模板②
]:
    out0 = b64encode(tmpl.encode())
    if len(s0) == len(out0):
        key = bytes(a ^ b for a, b in zip(s0, out0))
        break
```

★★ **两个模板都必须试**（v2.10.50 修复的真实 bug）：  
源站对**部分频道**（湖南/广州系、CCTV 付费频道、CETV、部分地方卫视、港澳台卫视）  
的第 1 条线路明文**少 `&type=.flv`** —— 标准模板 base64 后 136 字节，  
而密文解出来 124 字节，长度对不上 → 反推失败，报「密钥长度不符」。  
所以按长度试两个模板，命中即用。

### 6.3 三个坑

| 坑                               | 说明                                                                                                                                           |
| ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **① 域名必须同源**                    | `api` 必须是**当前生效镜像**。抓取走 api2、解密按 api1 造模板 → 长度相同但 XOR 出来的 key 是错的，13 条全部解坏（静默失败，不报错）。                                                        |
| **② Python 复刻时 raw string 的引号** | Rust 里 `r#""token="\+(\w+)\s*,\s*"token="\+(\w+)""#` 末尾那个 `"` 是 **raw string 终止符、不属于正则**。照抄进 Python 会多要求一个字面引号 → 永远匹配不上。`(\w+)` 是捕获组，括号不能转义。 |
| **③ 字节级替换**                     | 换 token / 去盐必须用字节操作（`replace_bytes`），不能用 `String::replace`（输入可能不是合法 UTF-8）。                                                                  |

实测输出（`python tools/_local_decrypt.py play ys 1`）：

```
HTTP 200  解密：ok  线路 13 条
  [ 0] eplay2  https://api1.2026016.xyz/eplay2.php?token=XA5T6KDvIVdhZ97TDE7XFuUR&tid=ys&id=1&p=0&type=.flv
  ...
  [12] eplay2  https://api1.2026016.xyz/eplay2.php?token=XA5T6KDvIVdhZ97TDE7XFuUR&tid=ys&id=1&p=12&type=.flv
```

★ 13 条线路 **token 全部相同、只有 p 不同** —— 所以**探活必须串行**，  
并发打 13 条会被源站限流（实测并发只有 1 条成功，串行 3 条都能出流）。

## 7. ⑤ 获取真实直播地址（302 链）

解密产物本身**不是流**，是源站中转口：

```
https://api1.2026016.xyz/eplay2.php?token=<T>&tid=<tid>&id=<cid>&p=<0..12>&type=.flv
```

它 302 到**两类**目标：

| 类型         | 形态                                                              | 后续         |
| ---------- | --------------------------------------------------------------- | ---------- |
| **A 直连真流** | `https://t62.iptv200.com:8443/live/cctv1.flv?sign=<ts>-<32hex>` | 直接用        |
| **B 二级中转** | `https://api1.2026016.xyz/v/migu8.php?token=..&id=<台标缩写>`       | 还要再 302 一次 |

`/v/*.php` 家族：`cqyx` / `ysp6` / `migu8` / `bstv` / `bstv1` / `hunantv` / `bfiptv`，  
参数 `token=<T>&id=<台标缩写>[&xra=<档位>]`（台标缩写如 `gzws`=贵州卫视、`cctv1`、`sjdl`…）。

★ **`/v/*.php` 不是解密产物，是 302 的中间跳**（早期文档把它误判为「被丢弃的中转线」）。  
★ `/v/migu8.php` **单独请求返 HTTP 500**，必须原样带上 Location 里给的 `token` 与 `id`。

本轮实测（`ys:1 p=0`）：

```
GET https://api1.2026016.xyz/eplay2.php?token=XA5T6KDvIVdhZ97TDE7XFuUR&tid=ys&id=1&p=0&type=.flv
→ HTTP 302
  Location: https://t62.iptv200.com:8443/live/cctv1.flv?sign=1792992153-4ee40cbde3ef798c585b7f750bbfa6ba
```

★★ **`sign` 首段是签发时刻的 Unix 时间戳**（`1792992153` ≈ 2026-10-26 13:22，与抓取时刻吻合），  
后段是 32 位 hex。→ **sign 有时效、不能长期缓存**，每次新播要重新解 302。

### 解析实现要点（`net.rs::resolve_stream_url`）

```rust
let cli = blocking_client_no_redirect();   // Policy::none()，不自动跟随
for _ in 0..4 {                            // 最多 4 跳
    let resp = cli.get(&cur).timeout(timeout_ms).send()?;
    if resp.status().is_redirection() {
        let loc = resp.headers().get(LOCATION)...;
        let next = 绝对化(loc);
        if next.path().ends_with(".php") { cur = next; continue; }  // 还是中转 → 继续跟
        return Ok(next);                                            // 真流
    }
    if resp.status().is_success() { return Ok(cur); }                // 直接就是流
}
```

★★ **只取响应头，绝不跟随、绝不读正文**。这是最关键的一条：

| 动作                     | 实测耗时                                |
| ---------------------- | ----------------------------------- |
| 只取 302 响应头（不跟随）        | **0.20 ~ 0.25s**                    |
| 跟随重定向并读流正文（= mpv 默认行为） | **11.8 ~ 20.9s**（6 次里 4 次 TLS 握手超时） |
| CDN 直连真流               | **0.6s**                            |

原因不是源站「处理慢」：**FLV 是永不结束的流**，跟随重定向后客户端会一直等正文，  
读操作被挂到超时。mpv 的出画窗口只有 12s，被这段首跳吃光 →  
**明明活着的线路被判「未出画面」**（实测 gt:50 愛爾達體育1台）。

所以 app 侧先自己解析出 CDN 真流地址再交给 mpv —— 首跳 20.9s → **0.2s**，出画 3~10s。

## 8. 探活判据

### 8.1 中转层（`eplay2.php`）

只看 **302 存在与否**：有 Location 就算这一跳活着（0.2s），不看目标内容。

### 8.2 真流层

```
GET <真流URL>   # 带 Range: bytes=0-0 或直接 GET，只看状态码
```

| 结果                         | 判定                                  |
| -------------------------- | ----------------------------------- |
| `200` / `206` / 其它 2xx、3xx | **活**                               |
| `404`                      | **死**（资源确定不存在 → 立刻换下一条，14s 降到 2.5s） |
| `418` 等其它 4xx/5xx          | **活**（连上了，交给 mpv 判更准；源站可能瞬时故障）      |
| 连接失败 / 超时                  | **不确定 ≠ 死**，仍然交给 mpv 试              |

★ 「连接失败不算死」是实测教训：境外流在本机系统 DNS 被污染（解析到 Facebook/Twitter 段），  
reqwest 直连必然超时，但 Chromium（嗅探时）自带 DoH 不受污染，且污染是间歇/按域名的 ——  
预检不该替 mpv 做这个决定。

### 8.3 死线的排布

实测 `tid=ty&id=28`（9 条）：

```
p=0,1  → pstatp 型（无 sign）       ✘ 死（404，11.7s 才返回）
p=2~5  → iptv200/2026016（带 sign） ✔ 活（200，0.6~0.7s）
p=6,7  → pstatp 型（无 sign）       ✘ 死
p=8    → 空 Location                ✘
```

死线**排在前面** → 探速必须覆盖足够多条（现为 9 条）、单条真流探活超时 1.2s、预算 20s，  
否则死线把预算耗光、后面的活线根本探不到。

### 最小 Python 复刻（分组 + 频道 + 302，已实测）

```python
import urllib.request, re, ssl
UA = ("Mozilla/5.0 (Linux; Android 9; SM-N9700 Build/PQ3B.190801.01311438; wv) "

# 302（不跟随）
class NoRedir(urllib.request.HTTPRedirectHandler):
    def redirect_request(self, *a, **k): return None
op = urllib.request.build_opener(NoRedir)
try:
    op.open(urllib.request.Request(eplay2_url, headers=H), timeout=10)
except urllib.error.HTTPError as e:
    print(e.code, e.headers.get("Location"))     # 302 + 真流地址
```
